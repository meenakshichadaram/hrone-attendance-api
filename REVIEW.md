# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-37) | Integer division truncation bug in grace period check: `int((punch_in - start).total_seconds() / 60)` truncates 10m 1s to 10m, causing `minutes > 10` to return `0` instead of `10`. Also assumes naive local date without IST or overnight shift date resolution. | Punch in at 09:40:01 for a 09:30 shift: starter returns `late_minutes = 0` instead of `10`, directly violating Rule R2. | Check `diff_seconds > 600` strictly in seconds before flooring minutes with `int(diff_seconds // 60)`, and resolve start instant based on IST shift calendar date. |
| 2 | `compute_work_hours` (lines 40-41) | Uses Python's built-in `round(..., 2)`, which implements banker's rounding (round-half-to-even) rather than round half-up as mandated by R4. Also lacks whole-second truncation (R1). | A duration of 2.125 hours rounds to 2.12 instead of 2.13. | Truncate timestamps to whole seconds and calculate duration using `Decimal` with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` (lines 44-47) | (1) Returns any overtime > 0, ignoring the 30-minute minimum threshold (R3). (2) Fails on overnight shifts by setting shift end on the punch-in calendar date instead of the next day. (3) Offset-naive vs offset-aware `TypeError` during subtraction. | Punching out 15 min after shift end returns `15` instead of `0`. An overnight shift raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Advance shift end by 1 day for overnight shifts, compute difference with timezone-aware datetimes, and return floor minutes only if `>= 30`, otherwise `0`. |

Contract requires 503 when MongoDB does not answer a ping. | Stop MongoDB or simulate connection failure; endpoint still reports 200 OK. | Issue `client.admin.command("ping")` inside a try-except block; raise `HTTPException(503, "Database unavailable")` if ping fails. |
| 5 | `create_employee` (lines 77-86) | (1) Check-then-insert race condition allows concurrent requests with the same `emp_code` to create duplicates. (2) Stores naive local time instead of UTC BSON date. (3) Returns `created_at` as datetime/string instead of epoch milliseconds. (4) Lacks schema validation (emp_code/email regex, shift_start != shift_end). | Send concurrent duplicate requests with the same `emp_code`; both insert. | 6 | `list_employees` (lines 88-96) | (1) Off-by-one pagination bug: `skip = page * page_size` means page 1 skips the first 20 records. (4) Returns `created_at` unformatted. | `GET /employees?page=1&department=Engineering` returns empty items and incorrect `total`. | Correct skip to `(page - 1) * page_size`, count filtered documents `count_documents(q)`, sort by `emp_code` ASC, and serialize timestamps. |
| 7 | `punch_in` (lines 99-122) | (1) No check for employee existence: missing employee causes `TypeError` (HTTP 500) instead of 404. (2) Check-then-insert race condition on `(emp_code, date)`. (3) `ts.date().isoformat()` ignores IST conversion and overnight shift rules (R1). (4) Returns illegal `"id"` field in response. (5) Accepts invalid statuses (ABSENT/LEAVE). | Punch in with non-existent `emp_code` -> 500 error. Send concurrent punch-ins -> duplicates created. Response contains schema-invalid `"id"`. | Check employee existence (404), enforce unique compound index on `(emp_code, date)` and catch `DuplicateKeyError` (409), calculate attendance date per R1, validate presence status enum, and omit internal `_id`/`id`. |
| 8 | `list_attendance` (lines 124-150) | (1) Performs unbounded query `list(db.attendance_logs.find(q))` loading entire collection into RAM before in-memory sort and slicing (fails at 100k docs). (2) Sorts by date only instead of `date` DESC, `emp_code` ASC. (3) Lacks validation for `date_from > date_to` (must return 422). (4) Returns illegal `"id"` field. (5) Returns raw BSON datetimes instead of epoch milliseconds. | Memory consumption spikes on large collections; `date_from > date_to` returns 200 instead of 422; response fails OpenAPI validation. | Execute `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` in database backed by compound index, validate date range, and serialize all instants to epoch ms. |
| 9 | Application Lifecycle & Indexes | No database indexes created on startup; application relies solely on MongoDB's default `_id` index. | Explain queries report `COLLSCAN`; duplicate keys are not prevented under concurrency. | Implemented startup index creation using FastAPI lifespan context manager for unique and compound query indexes. |
| 10 | Timestamp Serialization & Truncation | Instants were handled as naive datetimes and not truncated to whole seconds (R1), causing inconsistent time comparisons and leaking subsecond precision. | Subsecond values like `09:40:00.900` affected downstream calculations instead of being truncated to `09:40:00`. | Enforced whole-second truncation (`replace(microsecond=0)`) on all inputs and converted between UTC and IST at domain boundaries. |

## What was examined and decided was NOT a defect

1. **Identifying employees by `emp_code` instead of MongoDB `_id`**: The starter uses `emp_code` for all operations. This is not a defect; `DATA_MODEL.md` explicitly specifies that `emp_code` is the customer-generated business identifier and `_id` is internal only and must never be exposed or accepted.
2. **Storing `date` as `"YYYY-MM-DD"` and shift times as `"HH:MM"` strings**: This is intentional by design. As noted in `DATA_MODEL.md`, calendar dates and shift times are plain strings to prevent accidental timezone shifts and instant conversions.
3. **Omitting `work_hours`, `punch_out` on initial punch-in**: Storing `punch_out` and `work_hours` as `null` with `overtime_minutes=0` and `half_day=false` during punch-in matches the lifecycle state for open records.
